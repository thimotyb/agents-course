3. Agentic execution patterns

3.1 The tool-use loop

An agentic loop is a controlled execution cycle, not simply a longer chat exchange. The application sends the current messages and tool definitions to the model, inspects the response, executes any requested tool, and appends the tool result to the conversation before asking the model what to do next. The model therefore sees the evidence produced by its previous action and can decide whether another action is needed.

Loop control must rely on an explicit protocol signal such as stop_reason. A value such as tool_use means that the application must dispatch the requested tool and continue; end_turn means that the response can be returned to the user. Checking whether the first content block is text is unsafe because an assistant message can contain both explanatory text and a tool call. A maximum-iteration limit is still useful as a safety bound, but it should report an abnormal termination rather than replace the model's completion signal.

3.2 Model-driven versus fixed control flow

Model-driven control lets the agent choose the next tool from the current context. This is valuable when the route depends on information discovered during execution: a research agent may search, inspect a source, ask for a second search, and only then write a report. The architecture remains flexible because the developer specifies capabilities and constraints instead of enumerating every possible path.

Fixed control flow is preferable when the sequence itself is part of the requirement. A payment workflow, for example, may require identity verification, authorization, and a final commit in that order. The practical design question is not whether one approach is universally better, but which decisions should remain adaptive and which must be enforced by code.

3.3 Session state, resumption, and forking

Long-running work needs an explicit session strategy. Named resumption is useful when the previous conversation, tool results, and inspected files are still valid. The resumed agent should nevertheless be told about material changes made since the last run; otherwise it may trust observations that are no longer true.

Forking creates an independent branch from a shared baseline, which is useful for comparing two refactoring plans or testing alternative decomposition strategies. When the prior context is stale or too large, a fresh session with a compact, structured summary is safer than blindly resuming. This keeps state intentional and makes recovery reproducible.

4. Multi-agent and workflow architecture

4.1 Coordinator and subagent patterns

A coordinator-subagent architecture divides a complex task into roles while keeping responsibility for routing in one place. The coordinator receives the user request, chooses the appropriate specialists, supplies their inputs, aggregates their results, and decides whether the answer is complete. In a hub-and-spoke design, subagents return results to the coordinator rather than building hidden peer-to-peer channels.

This central point improves observability and error handling, but it does not create shared memory. A document analyst does not automatically see the search agent's findings, and a second invocation of the same subagent starts without the first invocation's context. The coordinator must pass the relevant findings explicitly, including source metadata, confidence, and any unresolved questions.

4.2 Decomposition strategies

Decomposition should match the shape of the problem. A predictable review can use a fixed sequence, such as analysing each file locally and then performing a cross-file integration pass. An open-ended investigation needs an adaptive plan: first map the problem, then create subtasks from what was discovered, and revise those subtasks when dependencies or missing evidence appear.

The coordinator must also check breadth, not only the quality of each individual result. If a research request about renewable energy is decomposed into solar and wind alone, downstream agents can work perfectly and still produce an incomplete report. A coverage assessment and targeted follow-up loop are therefore architectural responsibilities, not optional editorial steps.

4.3 Enforcement, handoff, and escalation

Prompt instructions are suitable for flexible guidance, but they cannot guarantee that a probabilistic model will always respect an ordering rule. When a missed step could cause a financial loss, a security breach, or a compliance violation, enforce the prerequisite in code. A refund handler, for example, should reject the call until the session contains a verified customer identity, even if the model tries to skip that step.

Escalation is another workflow boundary. A human reviewer may not have access to the agent transcript, so the handoff must be self-contained: identify the customer or case, summarize the request and attempted actions, state the suspected root cause and impact, and recommend the next action. For multi-concern requests, investigate the concerns in parallel where possible and produce one complete resolution or handoff rather than silently dropping the secondary issues.

5. Tools, MCP, and controlled capabilities

5.1 Tool contracts and selection

A tool description is part of the agent's decision surface. It should explain the tool's purpose, required inputs, output shape, boundary conditions, examples, and the situations in which a similar tool should be used instead. Vague names such as analyze or overlapping descriptions force the model to guess, which increases misrouting even when the underlying implementation is correct.

Tool access should be scoped by role. A synthesis agent may need a small verify_fact capability for common checks, but it should not receive every web-search and data-mutation tool in the system. Narrow interfaces reduce decision complexity, limit accidental side effects, and make it easier to reason about which agent is allowed to perform an action.

5.2 Structured errors and recovery

An error message such as “operation failed” gives the agent no basis for recovery. Tool responses should distinguish transient failures, invalid input, policy or business-rule violations, and permission failures. A structured response can include an error category, a human-readable explanation, an isRetryable flag, and any partial result that remains trustworthy.

Recovery should happen at the narrowest layer that has enough information. A subagent can retry a timeout with a modified query, while a coordinator should decide whether to switch specialists or continue with partial evidence. A valid empty search result is not the same as an access failure: treating both as errors either wastes retries or hides a real outage.

5.3 MCP servers, tools, and resources

Model Context Protocol separates discoverable content from executable actions. Use resources for read-oriented material such as catalogues or reference documents, and tools for operations that query, transform, or change external systems. This distinction gives the agent a clearer contract and helps reviewers reason about side effects.

MCP configuration also has an ownership dimension. Project-level configuration is appropriate for shared team tooling, while user-level configuration is better for personal or experimental servers. Environment-variable expansion keeps endpoints and credentials outside committed configuration. Multiple servers can be exposed at once, but their tools should still be named and scoped so that the agent can distinguish capabilities without relying on accidental keyword matches.

6. Prompt, schema, and reliability strategies

6.1 Criteria, few-shot examples, and structured output

Reliable prompting starts with observable acceptance criteria. Instead of asking an agent to “review the document carefully,” define what a complete result contains, which evidence is required, and how uncertainty must be represented. Few-shot examples are most useful for ambiguous cases and output formatting: they demonstrate the boundary between a valid finding, an unknown value, and a case that must be escalated.

Structured output turns those expectations into a contract. A JSON schema or tool definition should distinguish required fields from optional ones, constrain categorical values with enums, and allow nullable fields where the source may not contain an answer. This is safer than encouraging the model to fill every field, because the schema makes missing information visible instead of rewarding plausible invention.

6.2 Validation, retries, and batch processing

Validation has two layers. Syntax validation checks whether the response conforms to the schema; semantic validation checks whether values are sensible, internally consistent, and supported by the input. A retry should include the validation feedback and preserve the original task context, rather than simply repeating the same prompt and hoping for a different answer. Repeated failure should become an explicit escalation or review state.

Batch processing is an architectural trade-off, not an automatic cost optimisation. It fits overnight reports and other work that can tolerate delayed results, but it is unsuitable for a blocking merge check or an interactive decision. Each request needs a stable correlation identifier so that asynchronous results can be matched to the correct input, and the workflow must define what happens when a batch item fails or arrives incomplete.

6.3 Context, provenance, and human review

More context is not always better context. Large inputs can dilute attention, especially when many files or long tool traces are analysed in one pass. Focused local passes followed by an integration pass often produce more consistent results than asking one model call to hold every detail at once. Context extraction, compact summaries, and position-aware ordering help preserve the facts that actually drive the decision.

Reliability also depends on provenance. Each important claim should retain its source, retrieval time, and relationship to the evidence used to derive it. Conflicting or time-sensitive sources should be marked rather than silently merged. Finally, confidence should be calibrated against labelled validation data and reviewed with stratified samples, so human review focuses on document types, fields, or confidence bands where the system is genuinely weakest.

7. Scenario-based architecture workshop

7.1 Customer support resolution agent

Design verification gates, MCP tools, structured errors, and escalation for returns, billing disputes, and account issues.

7.2 Multi-agent research system

Build a coordinator that partitions research, passes source metadata, runs independent agents in parallel, and requests targeted follow-up when coverage is incomplete.

7.3 Developer productivity and continuous integration

Combine codebase exploration, scoped built-in tools, non-interactive execution, actionable review prompts, and machine-readable CI output.

7.4 Structured data extraction

Extract fields from unstructured documents, validate them, handle ambiguity explicitly, and route low-confidence cases to human review.

8. Guided lab and assessment

8.1 Build a reliable research coordinator

Implement a small coordinator with two scoped subagents, structured findings, parallel invocation, a coverage check, and a bounded refinement loop using a local runtime where possible.

8.2 Architecture decision record

Document why each pattern was selected, what is deterministic versus probabilistic, how failures propagate, and where a human must remain in the loop.

8.3 Completion criteria

  • Every tool has an explicit contract and structured failure path.
  • Every handoff preserves the context and provenance needed downstream.
  • Tests cover premature termination, missing context, policy violations, and incomplete coverage.
  • The final report includes trade-offs, observability signals, and follow-up improvements.

10. Key takeaways

10.1 Architecture heuristics

  • Make control flow, state transfer, and tool boundaries explicit.
  • Use deterministic gates for high-stakes rules and prompts for flexible guidance.
  • Design for recoverability: structured errors, provenance, observability, and human escalation.
